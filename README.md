# BAYLINK API

Run `npm test` for isolated HTTP, Socket.IO, security, search and AI behavior tests. Tests use in-memory models and block `.env` loading, MongoDB connections and external AI requests. Run `npm run check` for the server syntax check.

## Release order and stored workflow data

Upgrade and restart **all API instances before publishing the new frontend**. Include `lib/guideWebSearch.js`, `lib/plannerWebLibrary.js` and `lib/plannerTravel.js` with `server.js` and the changed modules; they are required at startup. An old API rejects new preference/cover fields and has no candidate-library, reschedule or time-poll endpoints. These new frontend actions do not have full old-API capability negotiation. During rollout or rollback, do not route new workflow writes to mixed API versions.

The production schemas persist private candidates and their revision in `PlannerAccount`, reschedule proposals/receipts/notification snapshots inside `ServiceBookingAgenda.bookings`, and covers/time polls in `Outing`. Existing records remain readable without a backfill or collection migration; optional values are initialized on first use. See [workflow deployment and persistence](docs/workflow-deployment.md) for compatibility, rollback and configuration details.

## Search and BayBay

- BayBay and its related helpers can use direct Claude API: unified research/planning, legacy guide answers, shared web search, event screenshot extraction, private conversation assistance, post drafts/translation, planner ranking and outing drafts. Set `BAYBAY_AI_PROVIDER=anthropic`, `ANTHROPIC_API_KEY`, `ANTHROPIC_WORKSPACE_ID` (required for organization-scoped keys), and `ANTHROPIC_BAYBAY_MODEL=claude-opus-5-5` on the server. `ANTHROPIC_BAYBAY_EFFORT` accepts `low` or `medium` (default); no sampling overrides or fast mode are sent. The default provider remains OpenAI. Claude failures never silently switch to OpenAI. Existing output validation, authentication and quotas still apply; drafts do not publish posts or send messages.
- Per-route Claude model, effort, output budget and deadlines, the dated price table and the daily/monthly micro-dollar spend ledger are described in [`docs/ai-models.md`](docs/ai-models.md). With no `BAYBAY_MODEL_*` / `BAYBAY_EFFORT_*` variables set, requests are unchanged.
- For temporary credits, `ANTHROPIC_USE_UNTIL` accepts an ISO UTC timestamp. Expired or malformed nonempty deadlines block new Claude calls, retaining deterministic site help and cached research. This is a time boundary, not a dollar budget or a credit-balance check. Provider quotas, authentication, cancellation and the eight-call request cap remain enforced. See [Claude rollout and verification](docs/claude-baybay-rollout.md).

- `GET /api/posts?keyword=...` uses literal matching with AND between up to 8 terms. Explicit synonyms include 租房/租屋/出租 and 二手/闲置; region terms also match their known cities. Category, visibility, author blocks and pagination are applied before results are returned.
- `POST /api/ai/guide-chat` accepts `{message, context?: {categoryHint, currentPath}}`. Clear requests for listings use a read-only provider search without an AI call. It scans up to the newest 200 candidates after category, location, room-type and public-visibility filters, returning at most 3 cards. Signed-in users' author blocks apply; administrators cannot obtain hidden posts through BayBay.
- `matchingPosts` contains only `id`, `title`, `city`, `budget`, `confirmedAt?`, `createdAt`, `status?`, `category`. Contact and author records are not returned or sent to the model. Contact-like text in card labels is redacted.
- Monthly budget comparisons require a clear upper limit and monthly unit in the question. A listing must have a single unambiguous monthly amount in its budget, or the same bare amount explicitly described as monthly rent in its title/body. Daily/weekly prices, ranges, starting prices, per-person amounts and unclear currency/units are not treated as a confirmed monthly price. Original posts are never rewritten by this search.
- `matchNote` explains recognized constraints and uncertainty; `responseMode` is `search`, `ai`, `fallback` or `web`. `degraded: true` means AI or retrieval failed/unavailable and the response is basic guidance, not completed search results. Active status alone is not proof of current availability.
- Knowledge questions receive relevant excerpts and source links from `data/guide-catalog.json`, generated from the frontend's guide data with `scripts/export-guide-catalog.ts`. Regenerate and copy this catalog whenever guide content changes. Catalog answers alone are not live verification. `searchMode: 'site'|'smart'|'web'` defaults to `smart`: eligible public local-discovery requests can use the shared web-search service, while site-only mode never calls it. `retrieval` reports the requested mode, actual scope and web status; failed web lookup is explicit and preserves the existing guidance.
- With the default OpenAI provider, post-assist requests have a 12-second request/body timeout; legacy guide answers allow 20 seconds and a 2,000-token output budget. With Claude selected, both allow 28 seconds: post drafts use at most 6,000 tokens and legacy guide answers 4,096, including thinking. Guide responses use plain-text numbered paragraphs with the same 1,200-character hard limit. The server accepts only completed output (`finish_reason: stop` for OpenAI, `stop_reason: end_turn` for Claude); unfinished or oversized answers degrade instead of being sliced mid-sentence. Existing per-IP quotas remain in place. Test-only fixture providers may be injected through `createApplication({ai: {guideChat, postAssist}})`; test mode otherwise refuses external AI calls.

## Planner discovery and explicit web lookup

- `POST /api/planner/recommend` still returns the existing event `suggestions` schema. It additionally returns `placeSuggestions: [{id, placeId, date, reason, reasons, unknowns, budgetStatus}]`, at most three published places. `excludePlaceIds` accepts up to 100 canonical IDs independently of the existing event exclusion list. Known opening dates, current closed-day schedules, geography, age limits, setting and admission constraints are enforced before AI ranking. Named venues and Chinese/English place categories are matched against the catalog; explicit place requests do not get unrelated events to fill the list. Unknown hours and meal/shopping amounts stay unverified. AI may rank only the actual bounded candidates supplied to it; its invented or ineligible IDs are discarded.
- `POST /api/planner/web-search` is a separate, explicitly clicked lookup. Accepts only `{query, locale?, date?, region?, city?}`: query 2–500 characters, locale `zh-Hans|zh-Hant|en`, valid ISO day, existing region ID, and city up to 80 characters. Omit empty optional fields. Private plans, account IDs, messages/history and arbitrary nested filters are rejected. No background search or public-catalog mutation occurs. The provider receives only this public query/context, never saved plans.
- Success is `{ok:true,responseMode:'web',checkedAt,answer,sources:[{title,url}],cached}`. Search citations come from actual Responses `url_citation` annotations for OpenAI or native `web_search_result_location` citations matched to returned Claude search results, following completed web tool calls; no generated source snippets are used. `answer` uses `[1]`, `[2]` markers referencing this source list. **Render those markers as visible clickable citations** and label web information as needing confirmation. Sources must be HTTP(S) URLs without credentials, unusual ports, literal IPs or local hostnames; DNS must resolve exclusively to public addresses. Visitor-hours and admission questions additionally make bounded source-page reads under the source-fetch safety checks; a successfully fetched same-origin visitor parent may also supply a source. Failed reads establish no facts. Source validation is point-in-time and cannot guarantee later redirects or changes.
- Success may additionally contain `candidates: [{id,name,city,summary,timeSummary,priceSummary,sourceUrls}]`, up to five private-discovery place cards. All fields except `id`, `name` and `sourceUrls` are nullable. With the default OpenAI provider, existing explicitly structured citation-backed cards are accepted. When those cards are unavailable, the OpenAI path may make one optional **text-only** Chat Completions call to extract places from the already obtained answer. This extraction adds no web tool calls. Every extracted field must contain internal `{text,evidenceQuote,sourceNumber}` evidence: the quote must be an exact answer excerpt containing its real `[n]` citation, the text an exact substring, and the number an actual validated source. Invalid names discard cards; unsupported details become null. Hand-written citation numbers are removed before extraction. Evidence quotes are internal excerpts of the search answer, never website quotations or source snippets. No address, coordinates, machine-readable hours, numeric admission fields or public-catalog writes are added. Render each card's `sourceUrls` as visible links and retain the date reminder; `checkedAt` is retrieval time, weekly schedules do not guarantee the selected date, and price summaries are not complete outing budgets.
- The optional OpenAI extraction uses `OPENAI_WEB_EXTRACT_MODEL`, then the existing `OPENAI_MODEL`, then `gpt-4o-mini`, independently of the web-search model. It uses [Chat Completions JSON mode](https://developers.openai.com/api/docs/guides/structured-outputs), `store:false`, at most 1,400 completion tokens, no tools and no retries. Its timeout is at most six seconds, shortened to the remaining original 20-second search deadline minus a safety margin; slow successful searches skip extraction. Extraction failure, malformed output or evidence rejection **preserves the original successful answer and sources**. `candidateStatus` is `ready` for usable cards, `none` for an explicit empty extraction, `unverified` when evidence rejected all proposed cards, or `unavailable` when extraction failed or could not run. These statuses contain no provider errors, queries or credentials. Each new search reserves its maximum web tool-call budget before provider execution; the final answer/cards/status are cached together and concurrent requests share both stages. The optional extraction is a separate model call with token usage, not another web tool call.
- Claude search skips all OpenAI extraction. Place cards use the conservative local name parser below, and visitor facts use exact deterministic source-page extraction; unsupported details remain unknown and unverified cards are omitted.
- Before spending the optional OpenAI extraction call, a narrow deterministic fallback accepts an explicit named subject of `NAME is located at`, `NAME is situated at` or `NAME is open`, only when the next real citation is within a contiguous 600-character answer span without another named-location section or heading. Generic subjects and citation-only lines are rejected. This yields a name/source card with all other fields null; it never converts the following address, opening claim or price into verified facts. The formatter's name evidence can likewise be reconstructed from its exact supplied name text and the next matching real citation, without trusting a model-retyped quote. Other fields still require their exact evidence. Original sanitized production answers are fixtures for both location and opening wording.
- [Official OpenAI web-search documentation](https://developers.openai.com/api/docs/guides/tools-web-search) establishes the Responses `web_search` tool and citation annotations. The default OpenAI path uses `https://api.openai.com/v1/responses`, `store:false`, required search, `search_context_size:'medium'`, `max_output_tokens:2400` and a default `max_tool_calls:2` ([Responses reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)). `OPENAI_WEB_SEARCH_MAX_TOOL_CALLS` accepts 1 or 2, with 2 as the default and hard cap. The second tool call is allowed to fill an evidence gap; a response is never labelled exhaustive. Default `gpt-4.1-mini` is independently configurable with `OPENAI_WEB_SEARCH_MODEL`; it does not inherit the older chat model setting. Account access and billing are not verified by local tests.
- With Claude selected, the [native web-search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool) runs through `https://api.anthropic.com/v1/messages` using `web_search_20260318`, `allowed_callers:["direct"]`, full returned search results and automatic tool choice. The existing `OPENAI_WEB_SEARCH_MAX_TOOL_CALLS` setting also bounds native `max_uses` to one or two; the default is two. Claude uses `ANTHROPIC_BAYBAY_MODEL` and a 4,096-token cap including thinking. Native tool errors, missing executed searches, incomplete responses and unsupported citations fail safely without another provider call.
- Missing credentials, disabled search, incomplete/uncited output, unsafe-only sources and provider failures return `503 {ok:false,error}` without fake results. Invalid requests return 400; exceeded quotas return 429. Searches have a 20-second timeout with OpenAI or a 35-second timeout with Claude. Per-IP limits are 5/minute and 20/rolling day, plus three concurrent calls per process. Before an uncached search starts, it atomically reserves the configured maximum tool-call count in the MongoDB `PostTranslationQuota` bucket `planner-web-search:UTC-date`, shared by BayBay and the planner across replicas/restarts. `PLANNER_WEB_SEARCH_DAILY_LIMIT` defaults to 100 units: with the default two-call allowance, this permits at most 50 new searches per UTC day. Failed calls and unused reserved units are not refunded. Setting the daily limit to 0 disables lookup; unavailable quota storage prevents a provider call. Successful results are cached for 600 seconds by query/context hash, maximum 200 entries per process; same-query in-flight calls are deduplicated and failures cool down for 30 seconds. Cache hits do not reserve more provider quota, although request-rate limits still apply. No query text or IP is added to application logs or stored in the quota collection.
- Product metrics add `planner_outing_adopted`, `planner_edit_applied`, `planner_web_search` to the existing day/event/locale counters. The client sends the web-search metric only after success; the search route does not double-count it. Extra identity, query, plan and source fields are rejected. Tests inject `ai.plannerWebSearch`, `ai.plannerWebExtract` and `plannerWebLookup`; test mode blocks real providers by default. The local suite validates provider payloads, exact extraction evidence, citations, URL/DNS checks, limits, cache, timeout and compatibility without a paid API call.

## Optional route estimates

`GET /api/planner/travel-capabilities` reports `{available}`. Production route estimates are **off by default** and require both `PLANNER_TRAVEL_ENABLED=true` and a server-only `GOOGLE_ROUTES_API_KEY` with Routes API access. `PLANNER_TRAVEL_DAILY_LIMIT` defaults to 100 new route requests per UTC day across instances; 0 disables estimates. These variables are optional: without them, the frontend keeps its external map links and existing user-entered travel allowances. Never put the key in a `VITE_*` variable or client bundle.

`POST /api/planner/travel-estimate` validates two published catalog places with venue-level coordinates, a future departure within 100 days and `drive|walk|transit`. Queries run only on user action, with a 10-second deadline, per-IP limits and an atomic shared quota; failures also consume the reserved request. The result is a temporary, attributed Google Maps text estimate. It is not cached, drawn over another map provider, or automatically written into a saved itinerary. Parking, station access and walking to entrances still require additional time.

## Public post translations

- `POST /api/posts/:id/translation` accepts only `{target: 'en'}`. It reads the published post from the database and returns `{ok, target, source, translation}`; both text objects contain exactly `title`, `description`, `budget`, and `timeInfo`. English-only posts return the original fields without an AI call. Original posts are never rewritten.
- Only publicly visible posts are eligible, including when the caller is an administrator. Deleted/hidden posts and signed-in viewers' block relationships return 404. Visibility, blocks and source content are checked again after a translation finishes. Contact preferences, private messages, comments and account details are not sent to the provider.
- Successful translations are cached in MongoDB by source-content hash, target and prompt version, with a 180-day TTL. Edits invalidate the hash without relying on `updatedAt`. Every cache lookup still requires current public access. Same-content generation is deduplicated within a process, and failed generations receive a 60-second cooldown.
- New provider calls are limited to 20 per IP per minute, three concurrent calls per process, and 300 calls per UTC day across instances/restarts using an atomic MongoDB quota. All translation requests, including cache hits, are limited to 120 per IP per minute. Optional environment settings are in `.env.example`. Cached results remain usable when the provider is unavailable or the daily budget is reached.
- With the default OpenAI provider, translation uses `OPENAI_TRANSLATION_MODEL`, falling back to `OPENAI_MODEL`, then `gpt-4o-mini`, with a 20-second timeout. With Claude selected, translation uses the configured Claude model, a 28-second timeout and a 6,000-token inclusive cap. Only completed JSON responses with the four bounded string fields are accepted. The validator preserves numeric strings, currency symbols, percentages, URLs and email addresses; unexpected output falls back to the original text in the frontend. Per the [OpenAI Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create), OpenAI requests use `max_completion_tokens`; GPT-5/o-series models use low reasoning without a temperature override. Validated cached translations can still be served after the Claude use window closes; no new provider calls are allowed.
- `tests/post-translation.test.js` covers access checks, edit/moderation races, persistence, limits, provider payloads and failures using fake providers only. Inject `createApplication({ai: {postTranslation}})` for isolated route tests; test mode otherwise refuses external AI requests.
